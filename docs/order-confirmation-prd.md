# 织见外贸订单确认产品需求文档

建议版本 R1　2026年9月18日

面向 Nick、项目协调人、产品研发及首批纺织企业试点团队。

## 01 推荐决定

**首个付费产品建议定位为纺织外贸订单确认助手。** 这是当前最容易验证的切口，尚不能据此认定它最能带动增长。 它接住已有售前产生的真实需求，包括有明确采购意向但尚未下 PO 的需求，将客户 PO、报价、规格、样品确认和后续邮件整理成一份有依据、可审核、可交接的订单确认包。企业继续使用原来的 ERP、CRM 和邮件，织见负责发现跨资料差异、推动确认和保留版本。

上一版售中售后 PRD 描述了长期业务全貌。本版根据商业化证据与开源项目核查，调整首期投入顺序：订单确认与变更核对先做；交付单据核对随后；客诉先提供轻量证据关联；完整应收、赔付执行及供应链协作按实际需求再扩展。现有售前 Demo 继续作为入口，本版是新增产品建议。

**研究结论：外贸 AI 已有真实付费需求，但不能把所有知名项目都称为已盈利。** 中国制造网 AI 麦可有产品级现金收入披露；UiPath 有公司级营业利润；多数专业订单、单证和售后 AI 的公开材料只能证明功能、客户部署或厂商披露的客户收益。本版把这些证据分开使用。

| 建议保留 | 建议调整 | 判断原因 |
| --- | --- | --- |
| 现有产品驱动售前，真实需求进入售中 | 首期只卖订单确认与变更核对 | 输入、核对依据和输出更容易定义 |
| 业务活动持续积累公司事实 | 不先做全公司的历史数据治理 | 当前订单即可产生有用数据 |
| 销售、跟单、技术、财务共享对象 | 财务先读取必要条件，暂不重建账务 | 降低跨系统交付成本与责任范围 |
| 为未来 Agent 保留标准接口 | 首版只需稳定流程及有限 AI 能力 | 多 Agent 编排本身不能证明收益 |

第一版必须交付的结果包括：逐行需求与承诺对照、冲突与缺项清单、原文定位、责任人确认、对外澄清草稿、可供现有 ERP 使用的字段导出，以及后续变更记录。仅生成总结或聊天回答不算完成。

**对老板的价值主张：让业务员和跟单少翻资料、少漏变更，更快形成可以继续推进的订单。** 实际净节省和付费意愿需通过试点证明；订单总额、警报数量和生成次数不直接计作 AI 收益。

以下 8 个项目中，只有 UiPath 在本轮核查中取得公司层面的公开利润数据；其余主要用于学习已经部署的工作流。效率与客户收益来自厂商案例，不能作为织见承诺。

| 项目 | 已核实信息 | 采用的产品做法 |
| --- | --- | --- |
| Conexiom | ADI 案例称每日自动处理 1,700 单，原录入需 5 分钟每单。公司利润未核实。[案例](https://conexiom.com/case-studies/adi-global-distribution-helps-improve-sales-effectiveness-with-conexiom) | 邮件 PO 进入、对照主数据、处理例外、连接 ERP；标准商品结果不能直接套用非标面料 |
| Rossum | Wolt 案例约每月 5 万张发票、平均 60% 自动化、审阅中位数 47 秒。[案例](https://rossum.ai/customer-stories/wolt/) | 提取必须接校验和审核；把剩余人工时间计入效果 |
| Nanonets | Schneider 案例 2025年12月至2026年3月处理 50 万页，90% 以上为匹配率，非准确率；提到重复上传的计费问题。[案例](https://nanonets.com/customers/schneider-electric) | 文档与文档核对、异常分派；业务去重和计费去重一起设计 |
| Raft | Navia 案例的 75% 自动化含 35% 完全自动及 40% 少量人工处理。[案例](https://raft.ai/resources/navia-freights-operational-transformation-through-ai) | 无人处理与辅助处理分别报告，依赖真实物流系统的数据 |
| Traydstream | 有 Vinmar 出口贸易文件预检查合作；交易处理额不是软件营收。[合作公告](https://www.traydstream.com/news/vinmar-engages-traydstream-to-boost-trade-digitalisation-and-automation) | 单证差异检查可作为第二工作流，不能保证银行接受文件 |
| HighRadius | 提供扣款理由、支持文件、价格差异与 ERP 应收协作；本轮未核实独立利润。[产品](https://www.highradius.com/software/order-to-cash/deductions-management/) | 客诉证据接上真实应收有价值，但必须取得财务资料和人员参与 |
| Fin | 官方价 0.99 美元每 outcome；其计费定义包括部分交接等情形，并非全部为客户确认解决。[定价](https://www.intercom.com/pricing) | 明确收费单位值得借鉴；客户沉默不能作为纺织验收或客诉结案依据 |
| UiPath | FY2026 收入 16.11 亿美元，GAAP 营业利润 5,700 万美元；非新 Agent 独立利润。[官方业绩](https://ir.uipath.com/news/detail/431/uipath-reports-fourth-quarter-and-full-year-fiscal-2026-financial-results) | AI 理解内容，代码执行金额、权限与状态规则，关键决定由职责人确认 |

这些项目共同支持一个产品顺序：先接住固定业务输入，利用已有系统和规则形成可审核输出，再逐步扩大自动执行范围。它们并不证明把更多功能放在一起，就会更容易盈利。

## 04 从案例到产品取舍

上一版的长期数据模型仍有价值，但首期同时做完整跟单、质量、客诉和回款，会引入多个购买人、多个系统及不同的验收口径。客诉可能单案价值大却频次低；仅凭想象无法判断它是否足以支撑持续订阅。

| 候选工作流 | 数据与验收条件 | 推荐顺序 |
| --- | --- | --- |
| PO 与订单资料核对 | 输入主要在本企业，能用历史资料标注差异和耗时 | 第一付费工作流 |
| 样品确认与规格变更 | 与首个工作流共用对象，体现纺织判断 | 作为订单确认的组成部分 |
| 出货单据一致性 | 可复用字段、版本和证据，但须补充交付记录 | 第二工作流 |
| 客诉证据包 | 可复用订单档案，须有真实案件和批次证据 | 轻量预留，按案件量决定扩展 |
| 回款与自动核销 | 要求财务系统、核销口径和授权 | 后置，先只读必要账款状态 |
| 全链生产与交期预测 | 企业可能拿不到上下游完整状态 | 当前不作为交付承诺 |

**差异化假设是纺织业务中的跨版本核对与确认。** 例如总幅与可用幅宽、每色起订量、成品与坯布、样品认可范围、检测方法、特殊后整理和计价单位。这些应成为可检验的规则与证据关系，而不是仅出现在营销文案里。

企业已有 CRM 或 ERP 时，试点必须比较三种路径：现有系统合理配置后的流程；现有系统加通用 AI 助手；织见。使用同类资料，比较端到端耗时、遗漏、复核负担、维护成本及权限要求。不能预设通用助手无法保存企业上下文。

如果现有系统能以更低总成本达到同样效果，适合提供集成或交付服务，而不是强行另卖一套产品。是否形成可重复软件收入，取决于规则、字段映射与交付方法能否复用。

先复盘最近约 20 个停滞或丢失的机会，判断资料澄清、规格认可或确认延迟是否确实影响推进。若主要瓶颈是需求不足、报价竞争力或供应可行性，应回到对应环节重新选题；订单核对不能替代这些问题。

**保留售前的增长连接。** 售前交接带入客户、料号和明确需求；订单确认结果返回销售：何处缺资料、哪些要求不匹配、哪些客户已明确认可。实际成单或回款从业务系统读取，不能因生成了确认包就计为收入。

## 05 开源复用的建议组合

开源项目用于降低通用技术成本，不证明纺织产品已经验证。以下是截至调研日的仓库核查结论，代码、模型权重、数据及第三方服务须分别确认授权；版本在实施时固定并再次核对。

| 项目 | 核查到的定位与许可 | 本产品建议 |
| --- | --- | --- |
| Docling | 文档结构、表格及内容解析；核心 MIT。[仓库](https://github.com/docling-project/docling)、[v2.128.0 许可](https://github.com/docling-project/docling/blob/v2.128.0/LICENSE) | 首选解析候选，先用真实 PDF 和表格评测；不能直接充当订单规则引擎 |
| PaddleOCR | OCR 与文档理解工具，Apache 2.0。[仓库](https://github.com/PaddlePaddle/PaddleOCR) | 中文扫描件评测后的可选补充，不预先维护两套全量管线 |
| Unstructured | 文档分区与提取，核心 Apache 2.0；托管服务另有条款。[仓库](https://github.com/Unstructured-IO/unstructured) | 作为 Docling 的对照候选，按格式覆盖与成本二选一 |
| LangGraph | 有状态 AI 流程，MIT。[仓库](https://github.com/langchain-ai/langgraph) | 多轮流程确有需要时再用；MVP 可用普通服务和任务队列 |
| Temporal | 持久工作流服务，MIT。[仓库](https://github.com/temporalio/temporal) | 跨日等待和大量连接器形成规模后再评估，首版不强制引入 |
| pg-boss | PostgreSQL 持久任务队列，MIT。[仓库](https://github.com/timgit/pg-boss)、[许可](https://github.com/timgit/pg-boss/blob/master/LICENSE) | 采用 Node 服务时可作为轻量候选；外部执行仍需业务幂等 |
| ERPNext | 完整 ERP，GPLv3。[仓库](https://github.com/frappe/erpnext) | 用作业务对象参考或无 ERP 客户的后续候选；已有 ERP 客户不迁移 |

**最小组合建议：现有织见前端 + 文档解析候选 + 结构化模型输出 + 自研订单规则及审核服务 + 关系型数据库 + 原始附件存储。** 先支持人工文件导入和一份 ERP 导出模板。最终解析器选择以试点样本结果决定，不以排行榜、星数或展示效果决定。

自己需要做的核心包括：企业和客户料号对应、规格与样品认可范围、字段权威来源、变更影响、审批及执行版本绑定、业务包导出、计费去重和质量评测。这些内容直接决定产品价值，不能外包给一个通用提示词。

关系型数据库承担已确认业务事实；附件存储保留原文；搜索索引辅助查询。首期字段核对主要通过稳定编号、结构化规则和明确引用完成，不要求先建立覆盖全公司的向量知识库。

以下说明用于技术选型筛查，不替代上线前针对实际部署方式的许可审查。公开源码、允许内部使用与允许转售多租户服务不是同一个问题。

| --- | --- | --- |
| Dify | 以 Apache 2.0 为基础带附加条件，涉及多租户和前端标识。[1.17.1 许可](https://github.com/langgenius/dify/blob/1.17.1/LICENSE) | 可评估原型或特定部署，不默认可直接白标为我们的多租户产品 |
| n8n | Sustainable Use License，有使用目的及商业服务限制，非普通宽松开源许可。[2.39.7 许可](https://github.com/n8n-io/n8n/blob/n8n%402.39.7/LICENSE.md) | 可评估企业内部连接自动化；嵌入或代售先确认授权 |
| MinerU | 核查版本含 Apache 2.0 基础及附加商业条件、在线服务归属要求。[4.0.2 许可](https://github.com/opendatalab/MinerU/blob/mineru-4.0.2-released/LICENSE.md) | 作为解析效果候选，不按旧资料认定为无附加条件的 Apache 项目 |
| Chatwoot | 核心 MIT，enterprise 目录另有许可。[仓库](https://github.com/chatwoot/chatwoot) | 客服入口有明确需求时评估，不能假定企业版及 AI 功能都免费可转售 |
| Twenty | 主体 AGPLv3 及应用例外，部分组件和企业功能适用不同条款。[仓库](https://github.com/twentyhq/twenty) | 暂不为已有 CRM 客户增加第二套 CRM；也不默认全仓统一 MIT |

本轮查看的 12 个仓库均有近期维护活动；维护活跃不代表安全、稳定、支持所有中文面料文件或适合我们的生产负载。星数与营收、准确率、服务承诺均无直接等价关系。

采用前完成四项小范围验证：同一批真实资料上的字段与定位效果；依赖及模型的许可清单；本地或指定部署环境的数据流；升级及故障恢复方式。首期只接入实际能证明净收益的组件。

**避免技术堆叠。** 同时部署多个 RAG、Agent、自动化、客服及 CRM 平台，会增加权限、状态和维护问题。先形成一套可信订单事实与动作接口，以后不同模型可以调用同一业务能力。

## 07 客户画像与 MVP 范围

首批目标是柯桥面料贸易或工贸企业中的一个外贸团队：已有 ERP 或电子产品表；有稳定的客户 PO、报价、规格或样品记录；销售与跟单存在重复核对；能指定技术或资料负责人。先选择一类面料及相近交易流程。

规模本身不是充分条件。试点前需要读取一周工作样本，确认资料量、每包耗时、变更频率和能否取得核对依据。主要靠口头经营、没有确认资料或业务量不足以覆盖价格的客户，先采用轻量服务或暂缓软件订阅。

| 范围 | 首版承诺 | 首版之外 |
| --- | --- | --- |
| 业务入口 | 现有售前交接、客户 PO 或明确需求、修订邮件 | 大量新增陌生客户获客 |
| 输入 | PDF、XLSX/CSV、图片或文本邮件；实际支持格式按评测公布 | 所有文件均可无差错识别 |
| 核对依据 | 已确认报价、规格、样品认可和企业主数据 | 未经确认的供应能力或工厂状态 |
| 输出 | 证据化差异、澄清草稿、确认记录、字段导出 | 自主定价、承诺交期或创建生效合同 |
| 系统连接 | 文件导入、一份 ERP 字段模板；试点可选一个授权邮箱 | 一次接齐所有 ERP 和聊天渠道 |
| 售后 | 关联订单证据、登记主张及责任人 | 自动赔付、结案、财务核销及供应商追偿 |

首次设置只确认企业产品范围、字段来源、关键规则、责任人和运行权限。之后新资料、回复、变更和到期检查自动触发工作；用户不需要每轮新建“Agent 开发任务”。内部保留可追踪的工作项用于恢复和审计。

销售负责需求和对外沟通，跟单负责关联及推进，技术确认规格与可行性，财务确认付款条件或相关例外。系统根据事项分派角色，不要求每笔普通订单都经过所有部门。

当前售前仍是交互 Demo。新 Demo、真实资料试点和生产运行必须分别标识；接入按钮、预置样本和页面动画不能被称为已经连接企业系统。

## 08 核心流程与功能要求

**FR01 接收与归属。** 原始文件进入后，记录租户、来源、时间、哈希和原始文件，关联客户、机会、企业料号及订单行。归属不确定时给候选并等待人员确认。同一附件重传不重复建立订单或收费；修订文件产生新版本。

**FR02 逐项提取。** AI 输出符合字段约定的候选值，并定位原文。每个值标明客户要求、企业承诺、供应方声明或 AI 推断。未知、歧义、冲突和不适用分别表示。提取失败可重试或人工录入，不能伪造成功。

**FR03 主数据与版本核对。** 将客户 PO 与已确认报价、规格和样品范围逐行比对。金额、成分总和、数量与单位等由代码规则校验；语义对应由 AI 提出建议并显示依据。规则结论与 AI 建议分开存储。

**FR04 差异分派。** 系统生成有负责人、截止时间和影响范围的确认事项：规格交技术，数量和流程交跟单，价格与客户表达交销售，账期例外交财务。提醒去重、限频、可暂停。同一问题补充资料后继续原事项，不新建一堆重复任务。

**FR05 发布确认包。** 责任人接受、纠正、拒绝或补证后，生成绑定业务版本的确认包。内部审核通过不等于客户接受，也不等于 ERP 已生效；三个状态分别记录。

| 确认包组成 | 内容要求 | 使用方式 |
| --- | --- | --- |
| 当前业务摘要 | 主体、料号、数量、单位、价格币种、规格和承诺版本 | 人员快速接手 |
| 差异与缺项 | 旧值、新值、来源、影响范围和状态 | 处理例外 |
| 证据与决定 | 原文位置、确认人、时间、适用范围 | 复核和追溯 |
| 对外草稿 | 澄清问题或确认内容，引用已确认事实 | 销售确认后使用 |
| 结构化导出 | ERP 外部编号、字段映射、规则版本及状态 | CSV/JSON 导出或后续受控写回 |

生成草稿可自动进行，对外发送默认由人员操作。将来接入自动发送时，必须按动作取得企业授权，并在执行前重验版本、对象及发送范围。

导出只代表文件已生成；应记录后续人工确认或系统回执，才可显示已进入 ERP。业务材料未经全部必需确认时可导出“待确认清单”，不能标为可执行订单。

## 09 纺织字段、规则和变更

一套可复用的数据结构不意味着所有面料采用相同规格。建立少量通用字段，再按针织、梭织及具体品类配置字段；原始表达始终保留，标准值可以为空。客户料号、企业料号和供应商料号各有命名空间，映射需带来源及确认人。

| 字段组 | 必须表达的差异 | 处理原则 |
| --- | --- | --- |
| 品名与状态 | 面料类别、坯布或成品、后整理、用途 | 相似名称只提示候选，不能直接合并 |
| 成分与性能 | 成分比例、克重、缩水、色牢度、测试条件和方法 | 数值相同而方法或条件不同，仍可能不可比 |
| 幅宽与数量 | 总幅、可用幅宽；米、码、千克；每色与总量 | 米码可精确转换；米与千克缺条件时禁止换算 |
| 颜色与批次 | 客户色号、企业色号、色卡版本、缸号或批次 | 照片仅供关联，不能证明色差、手感或批次质量 |
| 样品认可 | 样品编号、确认内容、确认人、时间及适用产品 | 认可颜色不等于认可缩水、全部性能或大货 |
| 商务条件 | 价格、币种、计价单位、数量阶梯、每色 MOQ、付款条件 | 比价须使用同口径；不自行承诺价格与信用额度 |
| 日期与交付 | 目标日期、企业承诺日期、触发条件、分批、地点 | “30 天”缺起算条件时追问，不生成确定交期 |

**FR06 变更分析。** 新 PO、客户回复或规格变更进入后，系统显示字段差异和受影响订单行。与变更字段相关的待审草稿和批准失效，需要重新确认；无关决定可保留。已发出的历史版本不可改写，需建立新的修订记录和通知事项。

**FR07 关键项闸门。** 金额、单位、规格容差、样品范围、交期和付款条件按企业规则标记为关键项。未解决的关键冲突阻止“可执行”确认包发布；人员可按权限批准例外，记录理由、有效范围和责任。不能通过降低模型阈值绕过业务闸门。

事实不是一个永远被覆盖的单值。需保留谁在何时提出什么、针对哪一版产品及订单、谁接受或拒绝，以及何时失效。来源优先级按字段和业务规则配置；“最新一封邮件”不自动推翻已经确认的规格。

**示例：** 已确认报价写“可用幅宽 150 cm、每色至少 1,000 m”，客户 PO 写“总幅 150 cm、两个颜色共 1,500 m”。系统应提出两个独立问题：幅宽口径不同；每色数量或 MOQ 条件不明。不能因为数值 150 相同就通过，也不能用总数量替代每色数量。

## 10 Demo 页面与演示故事

Demo 面向老板展示业务价值，面向执行人员展示依据与动作。保留当前售前入口，新增“订单确认”主入口，售后先以案件证据页展示后续方向。页面显示演示资料标识和数据来源状态。

| 页面 | 展示内容 | 必须能交互的动作 |
| --- | --- | --- |
| 工作总览 | 待确认订单、关键阻塞、资料更新时间、负责人 | 点击事项进入对应订单和证据 |
| 订单工作台 | 当前字段、差异、确认范围、资料与版本 | 选择差异、打开原文、接受或纠正候选 |
| 澄清与确认 | 问题草稿、部门意见、待客户确认项 | 修改草稿、记录回复、查看状态分离 |
| 确认包 | 依据、批准版本、未解决事项、ERP 导出状态 | 导出脱敏样例，查看后续修订影响 |
| 案件证据预览 | 客户主张、涉及订单行、批次及缺失资料 | 关联证据、分派补证，查看并未自动结案 |

**演示资料全部虚构，建议使用一笔 10,000 m 梭织面料订单。** 金额和效率卡片使用清楚标注的模拟数字；没有真实基线时只显示数量与待办，不展示“已节省金额”。

演示第 1 步：从售前机会进入，系统沿用客户、产品和需求。导入 PO 后出现幅宽口径冲突、数量单位缺失和只有颜色获认可的样品记录。

演示第 2 步：点击幅宽差异，同时看到客户 PO 与已确认规格的位置。销售可把 AI 提议纠正为“需客户澄清”，技术收到与自己职责相关的事项。纠正被保存为当前业务决定，而非立即变成全公司通用规则。

演示第 3 步：生成英文澄清草稿，销售审阅。录入客户明确回复后，解决一个问题，另一个仍保持未确认；按钮不能跳过阻塞直接显示订单生效。

演示第 4 步：补齐依据并完成内部批准，生成确认包和演示 ERP 导出文件。系统清楚区分内部已审、客户是否接受及 ERP 是否导入。

演示第 5 步：客户新邮件把数量改为 12,000 m。旧待发草稿被标记为需复核，变更影响数量、价格阶梯和交期确认，旧版历史仍可查看。打开未来客诉页，可直接定位到当时确认的版本。

演示必须包含一次无法判断、一次人工纠正和一次版本失效。老板应看见系统如何减少漏项，也能理解何时仍需员工决定。Demo 的验收是交互与逻辑完整；识别效果及商业收益必须另外用真实资料试点。

## 11 售中延伸、售后与增长回流

首版可以保留长期数据库接口，但只有取得频次、损失和资料依据后，才增加完整工作流。售后能力按“记录主张—关联事实—补齐证据—形成方案—确认执行”展开。

| 阶段 | 可由 AI 辅助的内容 | 扩展的前提与边界 |
| --- | --- | --- |
| 交付与单证 | 对照当前已确认订单、发票、装箱单等的数量、单位、主体和版本 | 先定义文件组合；一致不代表实物合格、实际出运或银行接受 |
| 交期协作 | 从企业可见的供应方邮件、记录提取承诺与变化，提示缺失状态 | 区分目标、承诺、实际；无工厂状态时不承诺预测准确率 |
| 客诉登记 | 提取客户主张、受影响数量、时间、订单行及附件 | 主张不是已证实事实；按批次及订单行定位 |
| 证据组织 | 关联样品范围、确认规格、验货或检测、装运记录及沟通版本 | 资料不足先补证，照片不能单独判定质量责任 |
| 处理方案 | 起草补货、复检、折让等备选，展示依据和待决项 | 商务、技术和财务决定适用方案；AI 不自行承认责任或赔付 |
| 应收协作 | 读取到期日、争议款、已到账及核销状态，生成对账和跟进草稿 | 到账与核销分别取自授权财务记录；不自行关闭应收 |
| 复购与产品反馈 | 汇总已核实的未满足需求、复购原因、客诉模式及补救结果 | 分开记录客户说法、业务事实、AI 假设和实际成交 |

**轻量客诉页的首期内容：** 一个案件编号、一个责任人、一组涉及订单行及批次、一份客户主张、已关联证据、待补资料和处理状态。它的价值是降低员工找资料的成本；暂不提供完整赔付计算、自动追偿或客服系统迁移。

投诉、交付、客户验收、付款和财务核销可以同时处于不同状态。不能因为货已发、客户未回复或客服草稿已发，就更新为验收成功、案件结案或已回款。

**回到售前的闭环：** 将经确认的交付限制、客户规格偏好、产品缺口、复购记录和信用变化交给售前。单次投诉只作为案件事实；形成通用产品规则前，需检查样本数量、适用范围和技术人员意见。背调是外部风险信息，订单履约及付款记录是企业内部事实，两者保留来源及时间。

新增模块的依据是客户数据：持续发生的同类事项、可取得的证据、明确负责人及可量化收益。不能为了补齐产品版图而让试点团队同时承担多个系统接入。

## 12 为未来 AI 协作建立的数据框架

最小数据框架从当前工作产生，不要求先清洗企业全部历史。每个对象有租户内稳定编号，与 ERP、CRM 等外部编号映射。原始资料、待核实表达、已确认事实和派生建议分开存储。

| 对象组 | 核心内容 | 事实或权限来源 |
| --- | --- | --- |
| 客户与产品 | 客户实体、联系人、企业料号、外部料号映射、规格版本 | CRM、ERP 或指定主数据负责人 |
| 业务事项 | 机会、需求、报价、订单及订单行、外部编号 | 相应业务系统与明确的内部确认 |
| 样品认可 | 样品编号、规格版本、认可内容、提出者、确认者、范围 | 可定位的确认材料；不得扩大认可范围 |
| 原始证据 | 文件哈希、版本、时间、来源、页码或单元格定位、访问权限 | 原始附件和授权系统记录 |
| 字段表达 | 原文值、规范值、单位、表达类型、来源、置信信息、状态 | 客户要求、企业承诺、供应声明或 AI 候选 |
| 差异与决定 | 比较对象、影响字段、规则版本、负责人、决定及理由 | 确定性规则及人员确认 |
| 确认与执行 | 业务版本、确认范围、批准人、对外状态、导出或回执 | 决策记录和实际执行结果分别保存 |
| 后续关联 | 交付、批次、案件、主张、补证、应收外部引用 | 后续业务资料及原系统；首版保留接口 |

每条可供 Agent 使用的事实至少包含：对象、字段或谓词、值及单位、来源定位、适用版本、有效范围、记录时间、确认状态、权限。实际需要时再引入有效起止时间；不把所有资料一律复杂化。

**纠正如何变成知识。** 员工修正当前订单的值，会产生带证据的修订；重复出现的料号对应或规则，可提交主数据负责人评审。只有获准的映射或规则进入共享配置。保留例外范围，避免一次误改污染整个企业。

**标准化的边界。** 统一对象、状态、单位表达、证据和接口；保留不同品类的扩展字段及企业规则。面料行业缺乏完全标准化，会增加语义理解价值，也增加真值缺失和错误成本，并不自动意味着适合全自动执行。

ERP 已管理的库存、会计账簿和正式订单仍由其负责。织见保存跨资料的表达、证据、差异和决定；需要展示 ERP 状态时记录来源与同步时间，失联或过期就显示不确定。

## 13 AI、代码和人员如何协作

第一版可以采用一个理解资料的 AI 流程配合确定性业务服务。未来增加更多 Agent 时，共用以下对象和接口，不互相传递难以追溯的聊天总结。

| 参与方 | 可以完成的工作 | 决定依据 |
| --- | --- | --- |
| AI 理解服务 | 识别资料、提取候选、建议语义对应、起草澄清和摘要 | 授权资料与明确引用，允许弃答 |
| 业务规则服务 | 单位换算、金额检查、状态迁移、权限、版本及计费去重 | 企业规则、代码及已确认事实 |
| 销售与跟单 | 确认归属、澄清客户表达、对外沟通及推进 | 业务职责与来源材料 |
| 技术与财务 | 处理规格和商务例外，确认相应范围 | 授权职责，不替代其他角色 |
| 执行连接器 | 导出、将来受控写回或发送、保存回执 | 特定动作授权及执行时版本检查 |

业务动作示例为“添加材料、提出字段候选、登记差异、解决事项、批准某版本、生成导出”。请求带租户、操作人或服务身份、对象编号、预期业务版本及幂等键；结果返回新版本和审计事件。AI 不能直接修改数据库表来跳过业务规则。

**事件触发：** 新资料进入、相关字段变更、责任人回复、约定期限到达或外部状态更新。通知和后台任务持久化；崩溃或重试后可以继续处理。同一事件重放不会重复创建订单、发信或收费。外部执行还需自身幂等与回执核查，不能仅依赖队列的交付保证。

**权限与资料处理：** 所有文件、记录、索引、导出和队列任务均执行租户及角色检查；财务条件按角色控制。对外模型的资料范围及保留配置与客户约定。文档内的指令作为待分析内容，不得改变系统权限或触发发送。原始附件访问受控，分享和导出有记录。

**可维护性：** 记录模型、解析器、提示词、字段配置和规则版本；版本升级先跑固定评测集。员工可纠正字段、回看证据、暂停流程；解析失败进入待处理区。首版应能导出企业事实和原始证据索引，避免客户因模型或供应商变化失去数据。

建议技术结构：现有前端、一个业务 API、PostgreSQL、对象存储及持久任务队列。Docling 是待评测的首选解析器；如采用 Node 服务，可评估 pg-boss 管理后台任务。没有实际复杂度之前，不引入多个并行 Agent 或大规模工作流平台。

## 14 功能验收与失败场景

以下是实施后的验收要求，尚未执行；Demo 仅验证其中的交互与状态。真实资料效果另按下一节评测。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| 01 | 同一文件重传或任务重试 | 不重复建单、生成事项或计费；保留接收记录 |
| 02 | 多客户存在相同料号 | 不跨客户自动合并；待确认映射有明确候选 |
| 03 | 多页表格、合并单元格、拆分订单行 | 不漏行或重复合计；不确定行进入复核 |
| 04 | 总幅与可用幅宽均写 150 cm | 提示口径不同并显示原文，不能自动通过 |
| 05 | 千克与米之间缺少换算依据 | 保持不可换算；不编造结果或精确价格 |
| 06 | 色样只获颜色认可 | 不显示全部规格或大货质量获准 |
| 07 | 缺少检测方法或交期起算点 | 标记缺项，草稿提出澄清，禁止伪造条件 |
| 08 | 同一事项出现互相矛盾的资料 | 保留双方表达及来源，不只取最新值 |
| 09 | 人员批准前后收到相关字段变更 | 旧待发草稿及相关批准失效，执行被拦截 |
| 10 | 变更与某项批准无关 | 不无差别清空全部批准；保留影响判断记录 |
| 11 | 内部批准但没有客户回复 | 客户接受状态保持未知；不得代客户确认 |
| 12 | 导出成功但 ERP 未确认导入 | 显示已导出、执行未确认，不显示 ERP 生效 |
| 13 | 关键冲突尚未解决 | 阻止可执行确认包；有权限的例外批准需留痕 |
| 14 | 客诉资料缺乏批次或质量证据 | 生成补证项，不归责、不自动赔付或结案 |
| 15 | 跨租户文件链接或后台任务 | 拒绝访问且不泄漏内容、摘要和存在性信息 |
| 16 | 邮件正文诱导系统改变指令或发信 | 不提升权限，不改变业务事实，不触发执行 |
| 17 | 服务中断或超时后恢复 | 恢复待办，外部动作不重复，失败可定位 |
| 18 | 人工纠正后重新运行或更换模型 | 已确认事实不被候选覆盖，版本及纠正可追溯 |

优先守住跨租户访问、错误对外执行、版本失配和关键字段未经确认通过等风险。关键字段误放行在验收集须为零，未解决项应正确停留待确认。任何此类失败阻止扩大自动化范围；抽样零失败也不能被描述为生产环境永不出错。

## 15 六周付费试点与效果评测

**试点目标是判断能否值得持续购买。** 一个外贸团队、一类主要面料、一个订单确认流程及一份 ERP 导出模板。先定义历史人工流程和当前软件能力，再评估织见的增量。六周是有数据和负责人前提下的计划，不是无条件交付承诺。

第 1 周完成流程观察、字段来源及权限确认，并测量无需额外追索即可取得核对依据的业务包比例。缺依据占主导时，先改善取证入口。选取约 50–100 份脱敏历史业务包，另保留未用于调试的客户格式与后续资料；每包应尽量包括 PO、确认依据和关键修订。复杂表格、扫描差、单位混用、冲突及缺件必须出现，不能只挑干净材料。历史回放只使用当时已存在的输入，后续确认可作标注依据但不得提前提供给系统。

第 2–3 周影子运行：系统输出不改变外部业务，由熟悉业务的人员标注和裁决。第 4–5 周选择低风险流程进入有人审核的实际导出。第 6 周复盘效果、总成本和使用意愿，决定继续、调整或停止。

| 指标 | 计算方式 | 首期决策口径 |
| --- | --- | --- |
| 净处理耗时 | 从收到完整程度相近资料到确认包可用的主动人工时间，含复核、纠错与必要维护 | 相对最佳替代方案，目标中位数净减少至少 30%，P90 不恶化；属待验证目标 |
| 关键差异漏检 | 未检出的关键差异数 / 人工裁定的关键差异总数 | 逐类报告；涉及错误执行的漏检先修复再扩展 |
| 差异提示有效性 | 被业务人员认定有价值的提示 / 全部提示 | 报告误报及处理负担，不以警报越多越好 |
| 字段与证据正确性 | 候选值和定位分别人工抽样判定 | 按字段风险及文件类别报告，不能用一个总准确率掩盖关键错项 |
| 人工参与程度 | 无人处理、有审核处理、返工处理分别计数 | 首期以辅助处理为主；不同口径不合并称全自动 |
| 推进时间 | 可比事项从进入到内部确认、客户回复、ERP 接收的不同间隔 | 区分人工处理和外部等待；成交变化仅作探索指标 |
| 实际使用与经济性 | 活跃团队、完成业务包、净节省、接入维护及付费意愿 | 出现可持续净收益且客户愿付续费才进入扩展 |

人工标注也可能有分歧：关键差异由第二位业务人员复核，争议保留，不把第一位人员意见自动当成真值。小样本同时给出分子、分母与错误类型；50–100 包只适合发现问题和初步判断，不足以证明极低错误率。

用配对或交叉分配的可比资料比较现有流程、现有流程加通用 AI、织见，控制重复处理的熟悉效应。记录文档长度、修订次数和复杂度。客户回复快慢、市场需求及销售能力会影响成单，六周试点不能将全部收入变化归因于系统。

## 16 商业模式、价格假设与经济门槛

**商业交付物叫“订单确认试点”或“订单确认服务”。** FDE 是我们深入现场、连接数据和完善规则的交付方式，不要求企业先理解这个术语。试点收费对应具体输入、输出、范围和验收，避免免费做出长期定制项目。

以下价格仅供验证，并非调研得到的市场均价或已证实付费意愿：六周固定范围试点 20,000 元；达到约定条件后，订阅参考 6,000 元/月，包含一支团队、约定额度和标准支持。额外系统接口或持续新增流程单独报价。试点成果和导出归属、退出办法及服务范围写清楚。

收费单位建议为“当月活跃业务包”：同一客户、同一商业订单及其修订关联到一个稳定业务包，同月重复上传、解析重试和正常修订不重复收费；同一业务包跨月再次发生处理时计入当月一次。试点前约定示例 1,200 包/月及页数上限，超限先提示并约定扩额，不暗中按模型调用次数追加费用。

| 经济情形 | 演示假设与计算 | 判断 |
| --- | --- | --- |
| 低业务量客户 | 200 包/月 × 每包净省 7 分钟 ÷ 60 × 人工全成本 120 元/小时 = 2,800 元/月 | 单靠人工时间难覆盖 6,000 元订阅；不适合重交付 |
| 较高业务量客户 | 1,200 包/月，同口径节省 16,800 元；另扣每月 4 小时客户维护投入 480 元，净值 16,320 元 | 有机会支持付费，但需真实基线和实际采用 |
| 试点后 12 个服务月投入 | 试点 20,000 元 + 其后 12 个付费服务月 × 6,000 元，按 12 个服务月摊销约 7,667 元/月 | 高单量示例价值/费用约 2.13；须另计客户试点接入时间及硬件等实际成本 |
| 供应方交付成本 | 月费 6,000 元；假设运行成本 1,500 元 + 支持 4 小时 × 250 元 = 2,500 元 | 稳定运行月直接贡献率约 58%；未计销售、研发、税费，非净利润 |
| 定制负担增加 | 同上，若支持变为 10 小时/月，总直接成本约 4,000 元 | 稳定运行月直接贡献率降至约 33%，不能无限追加人工服务 |

六周试点及首次实施成本另行核算：20,000 元能否覆盖数据整理、规则配置、连接器和现场人工，必须实际记录；上述月度贡献率不含这部分成本。

这里的“7 分钟”已扣除正常审核和纠错，另计的维护仅指管理员额外工作，避免重复计算。释放工时是产能价值；只有减少加班、外包或把时间投入有效业务时，才进一步转为现金节省或经营收益。

上述摊销覆盖试点加后续 12 个服务月，日历周期超过一年；不能与严格的前 12 个月现金流混用。正式报价应按试点起止、订阅起始和客户接入成本逐月计算。

收入增量、避免损失可单列佐证，不能把整单金额算作 AI 创造的收益。若未来尝试结果分成，先有明确归因与回款口径；初期固定试点费加订阅更容易验收和控制争议。

## 17 实施路线与共同项目上下文

**第一个演示目标：** 一笔订单从售前交接进入，展示两项真实类型的冲突、一次明确的无法判断、一次人工纠正、一份确认包和一次客户改需求引发的版本失效。先让企业家看懂可买的工作结果，再决定接入何种真实数据。

| 阶段 | 交付结果 | 进入下一阶段的条件 |
| --- | --- | --- |
| D0 交互 Demo | 现有前端扩展、脱敏样例、完整状态交互、可下载示例包 | 目标客户理解价值，愿意提供样本并指定负责人 |
| P0 付费试点 | 文件导入、解析与证据、差异规则、确认和 ERP 模板导出 | 净节省、关键风险、采用和成本达到共同约定 |
| P1 重复交付 | 可复用字段配置、接入模板、持久任务和客户隔离；按需求接一个真实 API | 第二、第三家同类客户能以更低交付成本上线 |
| P2 单证与售后 | 交付文件核对；有实际案件量时扩展客诉证据流程 | 模块分别有付费人、数据源和效果依据 |
| P3 更广协作 | 受控写回、应收协作、更多供应方事件和 Agent | 真实授权与回执、稳定质量和可持续单位经济 |

交付角色至少包括产品/现场业务负责人、负责前后端与连接的工程人员，以及客户侧销售或跟单负责人。技术和财务按事项参与。初期人可以兼任；人力安排与六周计划须在取得样本及接入条件后估算。

共享 Git 仓库保存：产品决定及理由、业务词典、对象与接口约定、规则说明、脱敏样例、评测方法、未决问题和变更记录。协调人组织审阅和分工，避免聊天中的决定不进入共同上下文。

客户原始邮件、合同、价格、联系人、账户凭证及真实业务附件存放在有权限的业务环境。仓库中的演示资料全部虚构或经充分脱敏。公司未来的 Agent 从授权业务接口读取事实；项目参与者则从仓库读取产品设计和实现约定，两个范围分别管理。

每次 PR 应说明解决的业务问题、影响对象或规则、验证证据及遗留限制。发现新的行业例外，先补充案例和规则决定，再改实现。不要把所有修订自动归为新的通用能力。

复用目标建议为前三家试点中至少两家共用同一核心流程和规则结构，第二、第三家交付工时明显下降；该目标尚待实际验证。若长期依赖每家单独开发，应按项目服务核算与定价。

**上线前的三项商业判断：** 客户是否有足够高的核对成本；现有软件加通用 AI 是否已经够用；第二家客户是否能复用第一家的大部分规则和接入方式。任何一项不成立，都应调整范围或采用一次性交付服务，而不是继续堆功能。

## 18 调研口径与待验证决定

本版共核查 14 个商业产品及 12 个开源或源码可见项目，信息截至 2026 年 9 月 18 日。来源链接已随案例与选型结论列出。财务证据优先采用正式披露；功能与客户效果采用厂商原始页面；开源选型采用官方仓库、许可和版本记录。

| 面料类型及常见规格差异 | 技术人员标注典型和争议案例 | 字段范围、规则与首批评测集 |

**最终建议：** 用订单确认包获得第一笔可验收收入，用日常确认和纠正沉淀公司事实，再以同一套订单、版本和证据关系延伸到单证、客诉与复购。售前的增长故事由真实需求、履约和回款逐步验证，不靠增加 Agent 数量来证明。
